TURFYSLOT: COOLIFY PRODUCTION DEPLOYMENT GUIDE (MONGODB)

This guide deploys the MongoDB-backed application using compose.yaml and either MongoDB Atlas or a self-hosted MongoDB replica set in Coolify. The Compose file does not create the MongoDB service; create/manage it as a separate private Coolify resource and attach the application to its network. The application uses one database per deployment and does not synchronize Atlas and Coolify MongoDB or PostgreSQL. Changing MONGODB_CONN alone does not copy records.

IMPORTANT PRE-DEPLOYMENT CHECKS

1. Both Compose files mount public images and private verification documents on separate persistent volumes. The uploads-backup service snapshots both directories; configure off-server backup copies and test a restore before accepting real photo uploads.
2. Nginx proxies /uploads/ to the API's public static-image route. Keep private verification documents outside the public uploads directory; they are served only through the authenticated admin API.
3. Before redeploying a deployment that already accepted image uploads, copy any files from the API container's old /app/uploads/public directory into the new uploads_public_data volume. Earlier versions did not persist this directory, so replacing the API container before copying it may permanently lose those files.
4. Copy application and upload backups off the VPS and test a restore. VPS volumes alone are not disaster recovery.
5. Ensure the selected MongoDB database contains the records to preserve. MongoDB is not synchronized automatically between Atlas and Coolify.

PREPARE

1. Read AGENTS.md and README.md and review compose.yaml, Dockerfile, deploy/nginx.conf, and deploy backup scripts.
2. Run the required tests, lint/type-check, and production build. Resolve failures before deployment.
3. Put the intended code on a private Git repository accessible to Coolify. Check that .env files, database dumps, encryption keys, passwords, and payment credentials are not committed.
4. Choose the production domain and configure its DNS A record to the VPS address. Decide whether the same domain will serve both the web UI and /api (the provided Nginx setup supports this).
5. Plan a maintenance window. Stop services that can write to the source database while taking the final backup and restoring it.

CREATE THE COOLIFY RESOURCE

1. In Coolify, create a Docker Compose application from the private repository and select the production branch.
2. Use compose.yaml for the web/API/Redis services; it does not provision MongoDB. For Coolify MongoDB, attach the API to the database's private network and use its internal connection URI. No PostgreSQL service is required.
3. Confirm Coolify builds the web and API images from the repository. The API container runs database/applySchema.js before starting server.js.
4. Route the public domain to the web service on its container port 80. Enable HTTPS using Coolify's certificate management.
5. Expose only the web service publicly. Do not expose Redis port 6379 or API port 5000 to the Internet. Do not open the Compose host port 8080 publicly.
6. Keep Redis, application data, and upload volumes on persistent storage. Do not delete these volumes when redeploying.

CONFIGURE COOLIFY SECRETS

Set values in Coolify's environment/secret settings, not in source files:

- CLIENT_URL=https://your-domain
- API_PUBLIC_URL=https://your-domain
- MONGODB_CONN with the selected database's connection string (use the private Coolify service connection string when self-hosting MongoDB); existing deployments may use MONGODB_URI as a fallback
- MONGODB_DATABASE=turfyslot (or the intended database name)
- If set explicitly, REDIS_URL=redis://turfyslot-redis:6379 for the bundled Redis service; do not use the generic redis hostname on the shared Coolify network.
- Independent JWT_ACCESS_SECRET and JWT_REFRESH_SECRET
- PAYOUT_ENCRYPTION_KEY
- SMTP_CONFIG_ENCRYPTION_KEY
- PUSH_SUBSCRIPTION_ENCRYPTION_KEY
- SSLCOMMERZ_CONFIG_ENCRYPTION_KEY
- SHURJOPAY_CONFIG_ENCRYPTION_KEY
- UDDOKTAPAY_CONFIG_ENCRYPTION_KEY

For an existing database, keep the exact encryption key values used for its saved encrypted values. Changing or losing a key can make those values unreadable. Keep protected copies of these keys separately from database backups; never send them in chat or commit them.

Use independent randomly generated keys in the format expected by the app (32 random bytes, base64 encoded, or 64 hexadecimal characters). Do not use example values or local development credentials in production.

VAPID and SMS variables are optional unless those services are enabled. Configure SMTP and payment-provider credentials through the authenticated admin UI after deployment. If the destination database is empty, set ADMIN_NAME, ADMIN_EMAIL, and ADMIN_PASSWORD only for initial seeding; remove the seed password afterward.

MOVE OR RESTORE THE EXISTING DATA

1. Schedule a maintenance window and stop every app instance that can write to the source database. Take a fresh restorable source backup and separately back up the local public/private upload directories.
2. Confirm the Coolify MongoDB destination supports transactions on a replica set or sharded cluster. A standalone MongoDB instance is not supported. Keep the database port private.
3. Ensure the destination has no application data. From a temporary MongoDB Database Tools environment that can reach both Atlas and the private Coolify service, use mongodump to archive the source database and mongorestore to restore it to the destination. Example commands and cutover checks are in README.md under "Move MongoDB Atlas data to Coolify-hosted MongoDB". Do not use --drop; stop and investigate if the destination already contains application records.
4. Keep the same database name and all existing encryption keys. Update MONGODB_CONN in Coolify to the destination's internal connection string only after restore and count reconciliation; keep DB_PROVIDER=mongodb.
5. Transfer existing uploads to matching persistent directories on the VPS and confirm ownership/permissions allow the API to read and write as needed.
6. Verify collection counts, the existing admin account, important booking/payment records, audit history, and uploaded files before resuming traffic.
7. Preserve the Atlas source and final backup until production smoke tests and a separate post-cutover backup have succeeded. Rollback requires stopping writes first and reconciling any data created after the cutover.

DEPLOY AND VERIFY

1. Deploy from Coolify and wait for Redis, API, and web health checks to pass. The API startup check verifies the configured MongoDB is transaction-capable.
2. Visit https://your-domain/api/health. It should report a healthy database and provider "mongodb".
3. Sign in with the existing admin account if data was restored. Run npm run db:seed-admin inside the API container only if the database is genuinely empty; never seed a fresh admin as a substitute for restoring the existing database.
4. Test the HTTPS site, login/logout, public turf listing and availability, owner/admin views, profile and turf images, and private-document access controls.
5. Configure the effective public API callback base URL in admin Payment Gateway settings. Confirm all provider callback URLs use the HTTPS domain and fixed application paths.
6. Use provider sandbox mode first. Test checkout, server-side payment verification, duplicate callback handling, cancellation/refund, and webhook delivery before enabling live payment credentials.
7. Test a backup and restore, including MongoDB and uploads. Copy backups off the VPS and protect them with access controls.
8. Monitor Coolify logs and resource/disk usage. Never expose secrets, full credentials, or private documents in logs or support messages.

GO-LIVE CHECK

Go live only after HTTPS, data restoration, durable upload serving, backups, admin access, payment callback verification, and the critical booking/refund smoke tests all succeed. If any check fails, keep public traffic and live payment processing disabled until it is resolved.
